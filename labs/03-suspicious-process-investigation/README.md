# LAB 03 - Suspicious Process Investigation

## Objective

The objective of this lab is to investigate potentially suspicious Windows process execution activity using **Sysmon** and **Wazuh**.

This lab builds on LAB 02 by moving from basic process monitoring to contextual SOC investigation.

Legitimate Windows commands were executed in a controlled environment to generate process chains that can also appear during reconnaissance activity.

### Investigation Flow

* Controlled command execution on Windows
* Sysmon Event ID 1
* Windows Event Log
* Wazuh Agent
* Wazuh Server
* Wazuh detection rules
* Parent-child process analysis
* SOC investigation

## Scenario

The goal of this lab was to simulate benign local discovery activity that could require investigation in a SOC environment.

Three legitimate Windows commands were executed from PowerShell through `cmd.exe`:

```powershell
cmd.exe /c whoami
cmd.exe /c hostname
cmd.exe /c ipconfig
```

These commands are commonly used for legitimate administration and troubleshooting.

However, the same commands may also appear during host reconnaissance after unauthorized access.

The purpose of the lab was not to detect malware, but to understand how process context helps an analyst determine whether activity is expected or suspicious.

## Detection in Wazuh

Wazuh received the Sysmon process creation events generated by the commands.

### PowerShell Spawning cmd.exe

When PowerShell launched `cmd.exe`, Wazuh applied:

* **Rule ID:** `92004`
* **Rule level:** `4`
* **Rule description:** `Powershell process spawned Windows command shell instance`
* **MITRE ATT&CK ID:** `T1059.003`
* **MITRE tactic:** `Execution`
* **MITRE technique:** `Windows Command Shell`

### Command Shell Child Process

When `cmd.exe` launched the final executable, Wazuh applied:

* **Rule ID:** `92032`
* **Rule level:** `3`
* **Rule description:** `Suspicious Windows cmd shell execution`
* **MITRE ATT&CK IDs:** `T1087`, `T1059.003`
* **MITRE tactics:** `Discovery`, `Execution`
* **MITRE techniques:** `Account Discovery`, `Windows Command Shell`

### Original Sysmon Event

* **Field:** `data.win.system.eventID`
* **Value:** `1`

Sysmon Event ID 1 represents a **process creation event**.

## Event Analysis

### whoami.exe

* **Image:** `C:\Windows\System32\whoami.exe`
* **Command line:** `whoami`
* **Parent image:** `C:\Windows\System32\cmd.exe`
* **Parent command line:** `"C:\Windows\system32\cmd.exe" /c whoami`
* **Integrity level:** `Medium`

Observed chain:

```text
powershell.exe
   └── cmd.exe
       └── whoami.exe
```

The relationship was confirmed by correlating the `ProcessId` of `cmd.exe` with the `ParentProcessId` of `whoami.exe`.

## Field Interpretation

* **`eventID: 1`:** Sysmon Process Create event.
* **`image`:** Executable that was launched.
* **`commandLine`:** Command line used to execute the process.
* **`currentDirectory`:** Directory from which the process was launched.
* **`user`:** User account associated with the process.
* **`parentImage`:** Process that created the child process.
* **`parentCommandLine`:** Command line associated with the parent process.
* **`processId`:** Identifier assigned to the process.
* **`parentProcessId`:** Identifier of the parent process.
* **`processGuid`:** Sysmon identifier associated with the process.
* **`parentProcessGuid`:** Sysmon identifier associated with the parent process.
* **`integrityLevel`:** Security integrity context of the process.
* **`rule.id`:** Wazuh rule that matched the event.
* **`rule.level`:** Severity assigned by Wazuh.
* **`rule.mitre`:** MITRE ATT&CK mapping associated with the rule.

## Parent-Child Process Correlation

One of the main objectives of this lab was to reconstruct process execution chains instead of reviewing alerts in isolation.

For example:

```text
powershell.exe
      │
      ▼
   cmd.exe
      │
      ▼
  whoami.exe
```

The `cmd.exe` event identifies PowerShell as its parent.

The `whoami.exe` event identifies `cmd.exe` as its parent.

The same pattern was observed with `hostname.exe` and `ipconfig.exe`.

Process IDs and parent process IDs provide additional evidence to correlate the events and validate the parent-child relationship.

---

## SOC Investigation Notes

The commands executed during this lab are legitimate Windows utilities.

Their execution alone does not prove malicious activity.

However, from a SOC perspective, their context and sequence can make them relevant to an investigation.

### Observed Activity

```text
PowerShell
   │
   ├── cmd.exe /c whoami
   │      └── whoami.exe
   │
   ├── cmd.exe /c hostname
   │      └── hostname.exe
   │
   └── cmd.exe /c ipconfig
          └── ipconfig.exe
```

The commands reveal different information about the endpoint:

* `whoami` identifies the current user context.
* `hostname` identifies the local system.
* `ipconfig` displays local network configuration.

Individually, these commands are common administrative utilities.

If they appear in sequence after an unusual login, remote access event, suspicious script execution, or another security alert, they may indicate reconnaissance activity and deserve further investigation.

### Questions an Analyst Should Ask

* Which user executed the commands?
* What process launched the command shell?
* Was PowerShell execution expected?
* Were the commands executed interactively?
* Did the same user execute all commands?
* Did the commands occur within a short period of time?
* Was there suspicious authentication activity before the commands?
* Was another process executed afterward?
* Was there related outbound network activity?
* Is this parent-child relationship normal for the endpoint?
* Is this behavior common for the user?

### Investigation Assessment

The activity was classified as **expected controlled lab activity** because all commands were executed manually to study endpoint telemetry and Wazuh detections.

No evidence of malicious behavior was observed.

## MITRE ATT&CK

### T1059.003 - Windows Command Shell

Wazuh mapped the execution of `cmd.exe` to:

* **MITRE ATT&CK ID:** `T1059.003`
* **Tactic:** `Execution`
* **Technique:** `Windows Command Shell`

This mapping is consistent with command execution through the Windows Command Shell.

### T1087 - Account Discovery

Wazuh also associated Rule `92032` with:

* **MITRE ATT&CK ID:** `T1087`
* **Tactic:** `Discovery`
* **Technique:** `Account Discovery`

For `whoami.exe`, this mapping is relevant because the command reveals the current user context.

However, the same Wazuh rule was also applied to `hostname.exe` and `ipconfig.exe`, even though those processes do not perform account discovery.

This demonstrates an important SOC principle:

> **MITRE ATT&CK mappings provided by detection rules must be validated against the actual behavior observed in the event.**

The detection rule provides useful context, but it does not replace analyst interpretation.

---

## Rule Interpretation

The alerts observed in this lab were generated by existing Wazuh rules.

No custom detection rules were created.

### Rule 92004

* **Description:** `Powershell process spawned Windows command shell instance`

Observed relationship:

```text
powershell.exe
   └── cmd.exe
```

### Rule 92032

* **Description:** `Suspicious Windows cmd shell execution`

Observed relationships:

```text
cmd.exe
   ├── whoami.exe
   ├── hostname.exe
   └── ipconfig.exe
```

A Wazuh alert does not automatically mean that the activity is malicious.

The alert indicates that the event matched detection logic considered relevant enough to investigate.

## Conclusion

This lab successfully demonstrated how legitimate Windows commands can generate security telemetry that requires contextual analysis.

The complete investigation flow was validated:

* PowerShell launched `cmd.exe`.
* `cmd.exe` launched Windows discovery utilities.
* Sysmon generated Event ID 1 for each created process.
* Wazuh Agent collected the events.
* Wazuh Server processed the telemetry.
* Wazuh applied existing detection rules `92004` and `92032`.
* Parent-child process relationships were reconstructed.
* MITRE ATT&CK mappings were reviewed critically.
* The activity was evaluated from a SOC perspective.

The activity was confirmed as benign because it was generated manually in a controlled environment.

## Lessons Learned

* Sysmon Event ID 1 records process creation activity.
* A single command can generate multiple process creation events.
* Parent-child process relationships help reconstruct execution chains.
* `ProcessId` and `ParentProcessId` can be used to correlate related processes.
* `ParentImage` identifies the process that created the child process.
* `ParentCommandLine` provides additional context about how the parent was executed.
* Legitimate Windows utilities can also appear during attacker reconnaissance.
* `whoami`, `hostname` and `ipconfig` are not inherently malicious.
* Security events must be evaluated in context.
* Wazuh rules represent detection logic, not proof of compromise.
* MITRE ATT&CK mappings should be validated against the actual event behavior.
* Related alerts should be investigated as part of an execution chain instead of independently.
* No custom Wazuh rule was required for this lab.

---

## Possible Improvements

* Correlate multiple discovery commands occurring within a short time window.
* Compare normal administrative activity with unusual user activity.
* Analyze additional legitimate Windows discovery commands.
* Add PowerShell logging in a future lab.
* Compare command execution from different parent processes.
* Correlate process execution with network activity.
* Create custom detection rules after establishing normal telemetry.
* Investigate process chains following suspicious authentication events.
* Add timeline reconstruction to future SOC scenarios.

---

## Final Takeaway

> **A process is not suspicious only because of what it is. Its parent, command line, user, sequence and surrounding activity provide the context required for a SOC investigation.**

This lab demonstrated the transition from basic process monitoring to contextual process investigation using Sysmon and Wazuh.
